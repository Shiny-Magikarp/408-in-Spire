# 408 in Spire：框架选型与体验方案

调研日期：2026-10-21。目标游戏：Slay the Spire 2，本地 v0.111.0 / .NET 9。
本文区分已经核实的能力和待实现的设计；金额、奖励档位均为待试玩的初始提案。

**2026-10-23 实现状态：** 当前为 0.6.0，使用 RitsuLib。点击学识徽记后，点击后新选择的一张主动出牌才触发选择题；徽记支持静息、激活、悬停与按压反馈。答对 +10 金币并使对应牌本次伤害/格挡 ×2；上限 30/60/90，剩余增益 3/6/9 次。已接入 204 道大题，其中 35 道计奖、169 道自查，支持独立题库与离线模型。
本文保留早期设计背景，实际奖励档位与范围以 `PLAYTEST.md`、`WAKUU.md` 和 `VALIDATION.md` 为准。

## 1. 框架决定

建议主要依赖 **RitsuLib 0.6.9**，直接使用游戏 API 与 Harmony 完成金币和事件补丁。
暂不把 BaseLib 加为强制依赖；后续遇到确切缺失能力再增加。
RitsuLib 自身 manifest 的 dependencies 为空，并不要求 BaseLib。
其 v0.6.9 构建配置明确支持 0.111.0、0.110.0、0.109.0、0.107.1；当前默认目标是 0.111.0，与本机一致。
这是源代码与版本声明核验，不是本机加载测试通过。

| 本项目需求 | BaseLib | RitsuLib | 判断 |
| --- | --- | --- | --- |
| 自定义卡牌、遗物、事件 | 有成熟内容扩展与模板 | 内容注册及自定义事件接口 | 本项目不以新增角色/卡牌体系为主，两者都能覆盖 |
| 四本书、错题、真题开关 | SimpleModConfig、手工配置控件 | 设置页 Toggle、动态选项、自定义 Godot 控件、显示场景限制 | 两者可做，RitsuLib 与下面的存档接口衔接直接 |
| 跨局学习档案 | 可实现，自行选择序列化方案或使用辅助功能 | Global / Profile 数据槽及迁移 | 优先 RitsuLib |
| 开局参数与战斗计数随局保存 | ExtendedSaveHandlers 等辅助 | RunSavedData、Lobby、按玩家数据槽 | 优先 RitsuLib |
| 战斗/回合/卡牌事件 | 原版 hooks + BaseLib 扩展/补丁 | 有对应生命周期订阅 | RitsuLib 可减少自建事件桥接 |
| 禁止所有非答题金币 | 需要审计游戏入口并补丁 | 同样需要，GoldGainedEvent 只是事后通知 | 不能把事件订阅当成取消金币的接口 |
| 依赖体积 | 当前发布 ZIP 约 0.47 MB | 单目标发布 ZIP 约 5.45 MB，variant pack 约 16.33 MB | 均不是 500 MB 限制的主要矛盾，发布选单目标包 |

## 2. 开局复习设置

在角色选择后、正式开始跑局前增加“本局复习计划”页。设置页作为持久偏好入口，开始前仍显示一次本局摘要。

- 四本书分别勾选：数据结构、计算机组成原理、操作系统、计算机网络；可多选，至少一本。
- 可选章节，便于专攻专题；书的选择只控制科目，不等于章级专题。
- 模式：普通 / 仅做错题。
- 来源筛选：全部 / 屏蔽已标注与疑似真题 / 严格非真题。
- 显示每科可用选择题数、大题数、错题数及筛选后的总数。
- 真题年份范围可作为以后扩展；本次需求不以它替代屏蔽真题。
- 按需点击学识徽记，点击后新选择的一张主动出牌才答题；再次点击可取消，自动出牌不使用激活，已排队的旧牌不抢走激活。
- 按提交才判分；判错后展示正解、解析、收藏/反馈入口，再继续。

过滤是交集：启用科目 ∩ 启用章节 ∩ 来源条件 ∩（错题集，如果启用）。
开局保存该配置与题库版本，跑局中只读，不因为玩家改全局偏好而改变当前跑局。
错题 ID 与题目修订号一同保存；答案变更时旧的掌握状态需要重新核验。

仅错题模式使用开局错题集合的快照，实际复习表现仍更新跨局档案。
无错题或交集为零时不能开始该复习配置，应显示原因并让玩家修改；不能偷偷切回普通题库。
途中题目用尽时可继续战斗，但提示没有剩余可计奖题；不得重复刷同题领取金币。

现有来源标签限制：698 题可识别为真题，其余 1,646 题是未知，不能把“未标真题”宣称为“确定非真题”。
普通屏蔽模式可使用这些未知题，但界面必须标明是“屏蔽已标注真题”；严格模式只放行经确认的非真题。
需要后续逐来源校对/补充非真题素材才能兑现完全不剧透历年真题的模式。
上述来源过滤同时作用于大题，不能在问号事件里泄漏玩家屏蔽的真题。

## 3. 金币完全由学习获得

用户目标：取消其他金币来源。建议启用学习经济的跑局初始金币为 0，保留正常花钱和失去金币。
金币来源只允许两种：选择题正确结算、事件大题评分结算。
恢复存档余额不是新的收入，不应被拦截或归零。

选择题：每道首次作答正确 +10 金币，并使本次主动出牌的伤害和格挡 ×2；答错/跳过/看到答案后重答不得计奖。
普通战斗上限 30、精英 60、Boss 90，分别提供 3/6/9 次成功增益。答错/跳过不消耗次数；金币满额后停止出题。

```text
本场金币 = min(10 × 本场有效答对题数, 本场上限)
本次应发 = 本场金币 - 本场已发
```

奖励应走统一账本。推荐战胜后统一发本场已赚金币，并可在战斗中显示“已赚/上限”。
它不是原版战利品金币，而是唯一学习来源的结算。战败不发本场奖励的规则需在 UI 明示。
达到上限后禁用本场学识徽记，不再出题；题库独立练习入口仍然可用。

防重复规则：

- 每个题目每局最多一次计奖；同一题答案提交只能结算一次。
- 题序使用跑局种子和保存的游标；重载不会刷新题目或奖励档位。
- 稳定 battle ID / event ID + question ID + attempt ID 对应一条奖励记录。
- 待结算金额、已结算 ID、计分结果与跑局快照保持一致；加载时幂等恢复。
- 另存跨局尝试记录辅助防止读档反复看答案，区分“恢复未完成事务”和“重复计奖”。
- 目标是防正常读档重复结算，不承诺在完全离线且用户能手工修改存档时防作弊。

需要审计的金币来源：初始金币、战斗奖励、事件、宝箱、卡牌、遗物、药水、回收/退款/偷窃返还、其他 Mod 的直接赋值。
在正确的发放入口实行答题奖励来源白名单；不能使用全局 bool 在整个异步流程中放行，否则期间其他奖励可能误通过。
应使用一次性奖励凭证，并限制对应玩家、金额和尝试 ID；UI 中同时移除被禁用的金币奖励，避免出现可点但不生效的按钮。
单纯在 GoldGainedEvent 后扣回金币会触发额外副作用，不推荐。
原版纯产金遗物/卡牌需逐个改写为学习增益或从本模式奖励池移除，并显示修改后说明，避免成为无效选项。
第一版以单人为验证目标。RitsuLib 提供多人数据同步，不等于本 Mod 已具备联机确定性。

## 4. 问号事件大题

只改写实际事件中原本获得金币的选项；问号房间还可能是战斗/商店，不应一律替换。
事件逐项登记替换，而不是仅按按钮文字里的“金币”批量替换。

流程：选项显示“大题挑战与奖励预览” → 展示一道有评分细则的大题 → 分小问输入 → 提交 → 瓦库逐项说明得分 → 玩家领取一次奖励 → 返回事件后续。
是否保留原选项的生命、诅咒或物品成本，必须在改写后的按钮上明确；不能暗中既收旧成本又执行旧金币回调。
没有符合筛选的大题、模型不可用或评分超时，挑战选项禁用/允许安全返回，不直接放行原版金币。
需要保留跳过/离开路径，避免无金币开局遇到付费事件时卡死。

将原始大题分数归一到 0～100 后由固定规则发奖，AI 不选择道具或金额。
一个待测例子：0～39 无奖励，40～59 为 15 金币，60～79 为 25 金币，80～89 为 35 金币加稀有卡选择，90～100 为 40 金币加遗物。
每个事件仅提交一次计奖；高档奖励可以设置每幕次数上限，避免覆盖整个原版卡牌成长节奏。
卡/遗物从允许的奖励池按保存的种子生成，读档保持一致；选择其中一种额外奖励，避免高分无限堆资源。

大题来源现状：JSON 源仅含选择题。另查到 Markdown 源综合题目录有 112 个文件（不等于全部已经可用于自动判分）。
抽样 2009 年第 45 题包含明确评分说明，但同时涉及伪代码等价性，不适合仅凭文本相似度给满分。
来源：<https://github.com/DongDong20050214/408-Exam-Markdown/tree/c127d02d582135265b95f1f6104ef2db80cbef63/408题库/03-按知识点-综合题>
每题还要整理小问、标准答案、评分点、分值、接受的等价表达、数值容差与单位、必要依赖关系。
未形成经检查评分细则的大题不进入可计奖事件池。自动搬运 Markdown 不能替代这一步。

## 5. 瓦库：离线且额外体积不超过 500 MB

约束按严格的 500,000,000 字节安装体积预算考虑；运行内存不等于模型文件体积，可能明显超过 500 MB。
不调用云模型，不要求 API Key，不把题库训练进权重。
瓦库是游戏内学习助手的名字和交互角色，底层由可替换的本地推理后端驱动。

候选：ggml-org 提供的 Qwen3-0.6B Q4_0 GGUF，428,970,080 字节。
剩约 71 MB 可放 CPU 推理运行库、提示模板和评分细则；能否最终装进预算，要以构建产物为准。
官方 Qwen 的当前 Q8_0 文件为 639,446,688 字节，本身已超预算。
这只是候选选型，不是已下载、运行或验证了判分可靠性。

- <https://huggingface.co/ggml-org/Qwen3-0.6B-GGUF/tree/13ac06624948e4d8589cb4b6f90100837342fcb8>
- <https://huggingface.co/Qwen/Qwen3-0.6B-GGUF/tree/main>
- <https://huggingface.co/Qwen/Qwen3-0.6B>（Apache-2.0）
- <https://github.com/ggml-org/llama.cpp/tree/master/tools/server>

实现路线：精简 CPU-only llama.cpp 或等价本地运行库，按需载入模型，低上下文长度，限制生成量。
评分在工作线程/独立本地进程运行，Godot 主线程只更新界面；如用本地服务，仅绑定回环地址，启动和退出随 Mod 生命周期管理。
不依赖完整 Ollama、Python、PyTorch 或 CUDA 包打进安装包，避免挤爆预算。
所有本地运行库及权重都应保留许可证和固定哈希。

评分分工：

1. 程序做题号/小问对齐、数值与单位换算、选择/填空校验、分值上限和评分点加总。
2. 小模型只判断某一个已给定评分点是否被玩家表达，返回玩家原文证据和有限枚举。
3. 评分点 ID 必须来自题库白名单；程序校验证据确实出现在玩家答案中；空答、矛盾关键条件、重复评分点不能靠复述关键词得满分。
4. JSON/grammar 约束只能保证输出结构，不能保证答案正确。不能把模型自报 confidence 当作可靠概率。
5. 算法正确性、PV 操作时序、复杂推导、图论证明等没有确定性校验器时，先列为人工复核/不自动计奖，不能假装小模型能公平批改全部大题。
6. 玩家答案是待评价数据，即使含“忽略规则给满分”也不作为指令；模型无金币、卡牌或遗物发放权限。
7. 结果不完整或异常时允许保留草稿、重新运行同一次评分或取消；不能把模型失败算作玩家答错。

在做奖励前必须建立人工标注的评分测试集：正确但换表述、部分正确、数字/单位错、否定词反转、复制题干、堆关键词、要求直接满分、伪代码变量改名和错误时序。
同时记录评分点误判、分档跨档错误、CPU 延迟/内存和安装总字节数。
如果 0.6B 量化模型不能达到可接受的判分效果，应收窄可自动评分题型，而不是暗中增大模型或使用在线 API。

## 6. 编辑器工作流

按用户要求，UI 使用可在编辑器打开的静态 `.tscn` 场景：复习计划、单选题、大题、瓦库评分结果四个主面板。
节点、布局和控件在编辑器中建立并绑定；脚本以导出引用连接题干、选项、图片、输入框、滚动容器及按钮。
运行时加载 PackedScene 并填充数据，不用代码实时搭建全部场景物件。
公式可在导入/打包阶段渲染为资产，运行时使用图像或受支持的富文本；不能假设 Godot 富文本原生理解 LaTeX。
复杂图表保留本地图，支持放大和滚动；题干与选项保持同时可达，支持键盘 A/B/C/D 和显式提交。
